# 微信小程序端开发方案（2026-08-12）

> 结论：以 iOS 为设计基准全量复刻 10 个功能模块，原生小程序 + TypeScript，四端共用同一套
> Supabase 后端。后端只新增一个 `wechat-auth` 函数。**真正的上线阻塞项不在代码，在主体资质**——
> 现有小程序是个人主体，而 AI 问答类小程序必须是非个人主体，这条线要立刻起跑。

## 1. 定位与原则

`miniprogram/` 与 `ios/` `android/` `web/` 平级，是第四个可独立构建的前端交付物。

沿用 README 已立的三条原则，不另起炉灶：

- **iOS 是设计与交互基准**，小程序复刻；同一功能不允许出现第四种逻辑
- **真实优先 + 静默回退**：接口失败回退 `DemoData`，不白屏
- **交互差异要有理由**：只有平台惯例能构成理由，实现方便不行

唯一允许的端间差异是**登录方式**——iOS 是邮箱密码 + Apple，Web 是邮箱密码，小程序走微信一键
登录。理由是平台惯例：在小程序里让用户敲邮箱密码，注册转化会很难看。

## 2. 技术选型

**原生小程序 + TypeScript**，开发者工具内置 TS 编译（`useCompilerPlugins: ["typescript"]`），
不引入 Taro / uni-app 之类的构建层。

理由：仓库既定路线本来就是「各端原生重建」（SwiftUI / Compose / React 三套），小程序再引一层
跨端框架并不能复用什么——`web/` 的 React 组件依赖 Tailwind 4 与 framer-motion，两者在小程序里
都不可用，能复用的只有类型定义，而类型本来就可以手工镜像。原生方案换来的是最小包体、无构建层
黑盒、以及 Skyline 的完整可用性。

### 2.1 Skyline 的决策留给 W0-0

Skyline 是性能更好的渲染器（原生渲染，不走 WebView），但它为性能**大幅精简了 CSS 特性集**，
`mix-blend-mode` 已确认不支持。而设计基准 `Theme.swift` 里全是极光渐变、conic 色环、发光与
毛玻璃——正是最容易踩 Skyline 空白区的一类样式。

所以 `app.json` 目前是 `"renderer": "webview"`（全局默认），只有 `pages/dev-skyline-smoke/`
单独配了 `"renderer": "skyline"`。这一页把七项有风险的特性并排铺开：

| # | 特性 | 谁在用 | 不支持时的兜底 |
|---|---|---|---|
| 1 | `linear-gradient` | 按钮 / 卡片色带 / tabBar 选中条 | — |
| 2 | `conic-gradient` | OrbView 光球 · 万花筒 | canvas 扇形逼近（冒烟页第 6 项已给出画法） |
| 3 | `backdrop-filter` | Sheet 蒙层 · 付费墙遮罩 | 半透明纯色 + 降低对比度 |
| 4 | `box-shadow` 发光 | kaleidoCard · 光球辉光 | 多层边框模拟 |
| 5 | `mix-blend-mode` | 万花筒六瓣折光 | canvas `globalCompositeOperation` |
| 6 | canvas 2d + RAF | 万花筒 / 波形 / 转盘的兜底路径 | **必须可用，无兜底** |
| 7 | `transform` 动画 | 转盘 · 卡牌翻转 | — |

**W0-0 的产出是一个二选一的结论**，写回本节：

- 七项基本可用 → 全局切 `"renderer": "skyline"`
- 关键项缺失 → 保持混合渲染：动画重的页面（Community 抽取 / Lab 转盘 / Diary 波形）用
  Skyline，其余留在 WebView

`renderer` 可以按页面配置，所以混合渲染不是妥协方案，是一个正常的工程选项。

> Skyline 的客户端门槛：安卓微信 8.0.33+（基础库 2.30.4+）、iOS 微信 8.0.34+（基础库 2.31.1+）。
> 低于这个版本会自动回落 WebView，所以两套渲染路径无论如何都要保证不崩。

### 3.1 包体

微信硬限制：单个分包 ≤ 2MB，总和 ≤ 20MB。CI 里的 `npm run size` 会拦。

**已知的一个问题**：`docs/design/assets/digital-human-yuan-v2.png` 单张 1.3MB（共享素材总共
才 1.9MB），而 Home tab 的 PersonaCanvas 要用它。处理方式是转 WebP（预计降到 ~250KB），并给
`scripts/sync-assets.sh` 加一条小程序分发分支——`docs/design/assets/` 是共享图片的唯一母版，
不能在小程序目录里另存一份。

## 4. 网络与鉴权

### 4.1 为什么不用 supabase-js

它依赖 `fetch` / WebSocket / localStorage，小程序运行时全都没有，体积也吃不下 2MB 主包。
后端契约本来就定死在 `supabase/functions/_shared/schemas.ts`（10 套 JSON Schema、28 个函数），
手写一层薄 REST 客户端反而更可控：

- Edge Function：`POST {API_BASE}/functions/v1/{name}`，头部 `apikey` + `Authorization: Bearer`
  + `Content-Type` + `X-Request-ID`，与 iOS / Web 完全一致
- 会话续期：`POST {API_BASE}/auth/v1/token?grant_type=refresh_token`，session 存
  `wx.setStorageSync`，提前 60s 续期，并发调用合流到同一个在途请求
- 音频上传：`wx.uploadFile` 打到 `create-diary-entry` 返回的上传票据

### 4.2 新增函数 `wechat-auth`

这是本方案对后端的**唯一**改动。

```
小程序 wx.login() 拿 code
  → POST /functions/v1/wechat-auth  { code }
      ├─ code2session(AppID + AppSecret) → openid / unionid
      ├─ service-role 查 / 建用户 wx_<openid>
      └─ admin.generateLink(magiclink) → verifyOtp 换 session
  → { access_token, refresh_token, expires_in }
```

- `verify_jwt = false`（登录前没有用户 JWT，与 `card-game-catalog` 同类），改用频控 +
  code 一次性消费兜底
- 用 `generateLink` + `verifyOtp` 而不是给用户设一个派生密码——避免在任何地方存密码
- **AppID / AppSecret 只存 Supabase Function Secrets**（源头 Doppler），与
  `DEEPSEEK_API_KEY` / `AZURE_SPEECH_KEY` 同一条红线，绝不进小程序包
- 需要补 `_shared/validate.ts` 的入参校验与单测；新建用户走的是既有 `profiles` 触发器，
  RLS 测试需要覆盖「微信用户只能读写自己的行」

> ⚠️ **`openid` 按 AppID 绑定。** 主体一旦变更并重开小程序，AppID 会变，已有 openid 全部失效，
> 账号体系要重做。所以主体必须在上线积累用户**之前**定死——见 §6。

## 5. 流式对话

对应 iOS `ChatStreamClient.swift` 与 Web `web/lib/chat-stream.ts`，三端共用一套事件契约：
token `{t}` / done / error。

小程序没有 `EventSource`，也没有 `fetch` 的 ReadableStream，只能用
`wx.request({ enableChunked: true })` + `requestTask.onChunkReceived`。两个坑已在
`core/net/` 里解掉：

**① 小程序运行时没有 `TextDecoder`。** `onChunkReceived` 给的是 `ArrayBuffer`，而分片边界是按
字节切的——一个汉字占 3 字节，完全可能「前 2 字节在这个 chunk，第 3 字节在下一个」。逐片独立
解码就会在每个边界吐一个乱码字符。`core/net/utf8.ts` 里的 `StreamingUtf8Decoder` 维护未消费
字节缓冲，只解码构成完整序列的部分，尾部残字节滚到下一片。

**② 行解析不能依赖空行分隔。** iOS 在 `ChatStreamClient.swift:100-103` 记过同一个坑：连续换行
会被合并、不稳定吐出，靠空行触发派发会把所有 token 攒住一条都发不出。本后端每个事件是单行
JSON，所以见到一个 `data:` 行即视为一次完整事件——三端解析策略在这一点上是一致的。

**降级路径**：基础库低于 2.20.2 或 `onChunkReceived` 不可用时，chunk 回调不触发，整段响应会在
`success` 里一次性到达，那时把整段 SSE 文本喂给同一个解析器即可。打字机效果没了，对话本身不挂。

**必须真机双端验证**：iOS 微信与安卓微信的 chunk 分片行为不一致，开发者工具模拟器测不出来。
这是波次 1 · B 的验收项。

## 6. 合规与上线

这一节是本方案里**周期最长、最容易被低估**的部分。四件事，可以并行，但都不能省。

### 6.1 主体：个人 → 非个人（最高优先级）

微信开放社区的明确口径：小程序服务内容涉及深度合成技术（AI 问答 / AI 绘画 / AI 换脸）就必须
补对应服务类目，而**个人主体尚未开放深度合成相关服务类目**，代码审核会因「类目/内容不符」驳回。

审核看的是**服务内容涉不涉及深度合成技术**，与调用谁的模型无关——所以换成微信自家的 AI 能力
也绕不过去。

**「用腾讯云/微信云开发的 AI 就不用管类目」是个常见误解。** 技术上确实可以直接调
（`wx.cloud.extend.AI` 从基础库 3.7.1 起内置），2026 年 1 月上线的《AI 应用及线上工具小程序
成长计划》也确实**个人主体可以报名**，给 1 亿混元 2.0 Token、1 万张文生图额度、6 个月免费
个人版云开发环境。但该计划的官方文档同一份文件里写明：

> 当前平台未开放个人开发者备案【深度合成】类目权限，个人开发者可上架与大模型交互无关的
> 线上工具小程序。

即：个人主体能进计划、能拿额度、能用云开发的 AI 能力开发调试，但上架时只能是「与大模型交互
无关的线上工具」。这个 carve-out 对万花筒不适用——README 第一条设计原则就是「AI 是前门，
不是四个功能之一」，摘掉 AI 对话剩下的不是这个产品。

**出路是个体工商户**：持有营业执照的个体工商户在微信小程序体系里属于非个人主体，可以申请深度
合成类目。多数地区可线上办理、几个工作日下证，成本远低于注册公司。

> 观察项：成长计划的措辞是「**当前**平台未开放」，说明政策可能松动。但不能把上线计划押在
> 这上面——主体升级是确定性路径，成长计划的额度在主体升级后照样能拿。

> 因为 `openid` 绑 AppID（§4.2），这件事必须在积累真实用户之前完成。现在还没有用户，是代价
> 最低的时间点。

### 6.2 类目资质：算法备案材料从哪来

申请「深度合成 > AI 问答」类目需要提交**技术提供方的《互联网信息服务算法备案》备案号**，以及
运营主体与技术提供方**双方盖章的合作协议**。

后端当前直连 DeepSeek 官方 API。DeepSeek 有算法备案，但单个 API 用户很难拿到盖章的合作协议。
推荐的解法是**换材料来源，不换架构**：

| 方案 | 类目材料 | 代码改动 | 四端一致 | 评价 |
|---|---|---|---|---|
| **DeepSeek 经国内云厂商中转** | 云厂商标准化出具 | `_shared/deepseek.ts` 的 `baseURL` + Doppler 换 key | ✅ | **首选**：模型不变则 prompt 零改动 |
| **腾讯混元 2.0** | 腾讯自有模型，材料最好拿 | 同上 + prompt 与结构化输出回归 | ✅ | **次选**：有 OpenAI 兼容端点 `api.hunyuan.cloud.tencent.com/v1`，改法与首选相同 |
| 阿里通义 / 智谱 | 厂商出具 | 同上 + prompt 回归 | ✅ | 前两项都不成时的备选 |
| 小程序端走 `wx.cloud.extend.AI` | CloudBase 出具 | 重实现整条对话链路 | ❌ | 不推荐，见下 |
| 维持 DeepSeek 官方直连 | 需 DeepSeek 盖章协议 | 无 | ✅ | 大概率拿不到材料 |

> 混元的一个注意点：成长计划送的 1 亿 Token 额度绑定**云开发用量**，从 Supabase Edge Function
> 直连混元 API 是按量付费的，拿不到那份免费额度。这不影响选型（额度本来也只够试用期），
> 但别把它算进成本模型。

推荐方案成立的前提是 provider 层足够薄——`supabase/functions/_shared/deepseek.ts` 只有 33 行，
通过 `apiKey` + `baseURL` 构造，只有 `llm.ts`（结构化输出）和 `chat-stream.ts`（流式对话）两个
消费方。换端点是**改一个文件加几个环境变量**的事，模型不变则 prompt 零改动、10 套 JSON Schema
契约不用重跑。

**待验证**：云厂商上架的 DeepSeek 版本是否包含 `deepseek-v4-flash`。只有 v3 / R1 的话要评估
降级影响，或退到第二行的换模型方案（那时需要重跑结构化输出稳定性回归）。

**为什么不推荐 `wx.cloud.extend.AI`**：现在的对话链路——prompt 工程、并行画像抽取、岔路口成形
判定、JSON Schema 结构化输出、`conversations` / `messages` 持久化、Langfuse 追踪——全部在
Supabase 的 `chat` 函数里。`wx.cloud.extend.AI` 是小程序端或腾讯云函数调用，完全绕开 Supabase，
意味着要么在云函数里把整条链路重实现一遍，要么小程序端的对话行为与其他三端分叉。这直接违反
「三端对齐优先于单端最优」。

### 6.3 域名备案与反代网关

小程序的 `request 合法域名` 必须是已 ICP 备案的域名，不接受 IP、localhost 或未备案域名，且强制
HTTPS。后端当前是 `gxmruqzcyahjlktshpkh.supabase.co`——未备案，**不能直接用于生产**。

```
api.<备案域名>  →  国内主机 Nginx  →  gxmruqzcyahjlktshpkh.supabase.co
```

反代要点：

- **SSE 必须关 `proxy_buffering`**，否则打字机效果会被缓冲吃掉，退化成整段返回
- 透传 `X-Request-ID`（后端 `_shared/errors.ts` 靠它做关联锚点）
- `request` / `uploadFile` / `downloadFile` 三类合法域名都要配

开发期不必等备案：`project.config.json` 里 `urlCheck: false`，开发者工具勾「不校验合法域名」。
网关就位后只改 `src/core/config.ts` 的 `API_BASE` 一处。

### 6.4 隐私协议授权

2023 年起，调用录音、相册等隐私接口前必须先展示隐私协议并取得授权（`wx.requirePrivacyAuthorize`）。
这是 Diary 录音的前置，属于波次 2 · F 的验收项。`app.json` 的 `permission.scope.record` 已写好
用途说明。

### 6.5 付费墙

维持现有的 demo mock 解锁（写 `unlocks` 表），**不接真实支付**。小程序的虚拟商品支付在 iOS 端被
微信/苹果规则禁止，且个人及个体工商户主体开通虚拟支付本身就有门槛。真实 IAP 仍按 README 路线图
走 iOS 的 StoreKit 2。

### 6.6 埋点通路也被域名白名单卡住

「request 合法域名只接受备案域名」这条限制不止影响后端 API —— **PostHog 与 Sentry 的域名
同样进不去**，posthog.com / sentry.io 不在我们名下，备不了案。所以小程序端的客户端埋点
只剩 Supabase `app_events` 一条通路（经自有备案域名的反代网关），外加微信自带的 We 分析
（内置能力不需要配域名，但数据出不来、无法与业务表 JOIN）。

**后果**：`app_events` 在 iOS 上是「兜底事实表」（漏了还有 PostHog 兜着），在小程序上是
**唯一**事实来源 —— 漏报即永久丢数。所以 `core/analytics/` 的队列落本地存储、冷启动重放、
切后台立刻 flush，而不是像 iOS 那样只用内存缓冲。

配套后端改动：迁移 `20260812090000_app_events_miniprogram_source.sql` 把 `source` 放开到
`('ios','miniprogram','server')`，并给 `can_insert_app_event()` 补 `auth_wechat_started`。
纯放开，`ios`/`server` 判定不变；客户端仍然伪造不了 `source='server'` 与未知事件名。
详见 `docs/engineering/埋点方案.md` §0.1。

`W0-4` 与 `W0-1..3` 完全并行（目录不重叠）。

与真机有出入。跑法见 `miniprogram/README.md`。

### 波次 0 落地时发现的三件事（已解决，记录以免重复踩）

1. **内容侧不需要后端补 action。** iOS 用 supabase-swift 直读 `traveler_details` /
   `traveler_services`，一度以为小程序没有 SDK 就得让后端加 `get_traveler_detail`。
   实际 PostgREST 本身就是 REST 接口，`wx.request` 直接打即可——supabase-js 底下发的
   也是同样的请求。见 `core/net/request.ts` 的 `restSelect()`。
2. **`app_events.source` 有 CHECK 约束。** 原本只允许 `('ios','server')`，且
   `can_insert_app_event()` 里也把 `p_source = 'ios'` 写死了。已由迁移
   `20260812090000` 放开，并补了 `auth_wechat_started` 事件。
3. **小程序端只有 Layer 1 埋点。** 见 §5 的补充与 `docs/engineering/埋点方案.md` §0.1。

### 合并顺序

`W0-1..3` 先合入 → `W0-4`（后端，目录不重叠可随时合）→ 波次 1 三个分支逐个 rebase 合入
（目录互斥）→ 波次 2 五个分支同理 → 波次 3。

### 通用约束（写进每个 agent 的 prompt）

1. 保持「真实调用优先 + 本地兜底」，不得因接线失败让页面白屏
2. feature agent 不得改 `core/`、`app.*`、其他 feature 目录
3. 页面 wxss 不写死色值/字号/圆角，一律引 `tokens.wxss` 变量
4. 后端改动必须过 `pnpm test`；涉及表/RLS 必须补 `supabase/tests/` 用例
5. 密钥只存 Supabase Function Secrets，不进小程序包
6. 提交信息沿用仓库中文 conventional commit 风格，scope 用 `miniprogram`

## 8. 风险登记

| 风险 | 影响 | 现状 / 对策 |
|---|---|---|
| **个人主体开不了 AI 问答类目** | **上线阻塞** | 注册个体工商户；必须在积累用户前完成（openid 绑 AppID） |
| **拿不到算法备案盖章材料** | **上线阻塞** | 改走国内云厂商中转 DeepSeek，材料由云厂商出具 |
| 域名未备案 | 上线阻塞 | 并行推进 ICP 备案 + 反代网关；开发期 `urlCheck: false` 不受影响 |
| 云厂商无 `deepseek-v4-flash` | 需换模型 | 待验证；退路是腾讯混元 2.0（OpenAI 兼容端点，改法相同）+ 结构化输出回归 |
| Skyline CSS 缺特性 | 动画保真度下降 | W0-0 冒烟先验；`renderer` 可按页配置，混合渲染是正常选项 |
| 安卓/iOS 微信 chunk 行为不一致 | 打字机效果异常 | 波次 1 · B 真机双端验证；已有整段降级路径 |
| 主包超 2MB（1.3MB 数字人图） | 提审失败 | 转 WebP + `sync-assets.sh` 加小程序分发分支；CI 有 `npm run size` 护栏 |
